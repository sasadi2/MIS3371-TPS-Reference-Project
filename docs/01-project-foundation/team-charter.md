# Example Team Charter

> **Reference note:** Student teams should replace these example roles with their actual team members, responsibilities, and agreed working practices.

## 1. Team Objective

Deliver a complete, consistent transaction-processing capstone in which documentation, diagrams, code, testing, and GitHub history all describe the same approved business scenario.

---

## 2. Example Role Distribution

| Role | Primary Responsibility | Evidence of Contribution |
|---|---|---|
| Team Lead | Coordinates deadlines, integration, contribution tracker | Meeting notes, merged work, tracker updates |
| Business / Requirements Lead | Requirements, rules, traceability | Requirements docs, review comments |
| Design / Data Lead | Workflow, states, data dictionary, architecture | Design docs and diagrams |
| Client-Side Lead | HTML/CSS/JavaScript integration | Commits to client-side files |
| Testing / Integration Lead | Test cases, integration checks, release review | Test evidence, issue tracking |

Roles do not mean only one person may work on an area. Every member is expected to understand the full project.

---

## 3. Working Agreements

- Major work is committed to the shared GitHub repository.
- Important design changes are discussed before implementation.
- No member should overwrite another member's work without coordination.
- Each member should make meaningful contributions throughout the semester.
- Team documentation should remain consistent with implemented behavior.
- Problems should be raised early rather than hidden until a milestone deadline.
- Team members should review one another's work before final submission.

---

## 4. Contribution Tracking

For each major activity or milestone, the team lead records a contribution score from `0–100` for each member based on observable work.

The contribution tracker is:

- visible to the full team,
- supported by brief evidence when a score is unusually low,
- not itself the official course grade,
- one source of information that may be compared with GitHub history and submitted work.

---

## 5. Definition of Done

A team artifact is not considered complete merely because a file exists.

It should be:

- understandable,
- scenario-specific,
- internally consistent,
- reviewed,
- committed to the repository,
- ready for another person to inspect without verbal explanation.
